# Контрольные вопросы

1. **Что такое кеш?** Это временная копия данных для более быстрого чтения. Ускорение имеет смысл, если возможная задержка обновления контролируется TTL или инвалидацией.
2. **Как работает cache-aside?** API сначала читает Redis. HIT возвращает найденное значение. При MISS API загружает данные из PostgreSQL, записывает их в Redis с TTL и возвращает результат.
3. **Зачем TTL?** Он ограничивает время жизни записи, освобождает память и удаляет ключи старых версий.
4. **Какие данные кешировать?** Сводку по площадкам и повторяемые фильтры, потому что их вычисление дороже чтения Redis. Редкие уникальные запросы и часто меняющиеся дешёвые карточки дают меньший эффект.
5. **Как построить ключ списка?** Включить ресурс, версию и хеш фильтров, поиска, сортировки, страницы и лимита. Иначе разные запросы могут получить один и тот же результат.
6. **Что такое инвалидация?** Это исключение устаревших данных из дальнейшего чтения. EventManager меняет версию набора при записи, а Redis удаляет старые ключи по TTL.
7. **Зачем версия списков?** Смена версии делает сразу все сочетания параметров прежнего набора недоступными для новых запросов. Поиск и удаление всех таких ключей в момент записи не нужны.
8. **Зачем обработка отказа Redis?** PostgreSQL остаётся источником данных. При сбое Redis API выполняет запрос в базу. Версии продолжают меняться, поэтому устаревший кеш после перезапуска не используется.
9. **Что значит X-Cache?** HIT — чтение из Redis, MISS — запрос в БД с заполнением кеша, BYPASS — запрос в БД с обходом Redis.
10. **Почему карточка выигрывает меньше отчёта?** Карточка уже читается по индексу первичного ключа. Отчёт агрегирует много строк, поэтому кеш экономит больше работы.
11. **Что такое холодный и тёплый кеш?** Для холодного ключа ещё нет значения, поэтому первый запрос оплачивает SQL и запись в Redis. Тёплый ключ уже заполнен.
12. **Что показывают метрики?** Среднее описывает типичный общий уровень задержки, p95 показывает границу для 95 % запросов, RPS — число запросов за секунду. Повторные измерения выявляют разброс.
13. **Зачем большая база?** Семь строк почти не нагружают поиск, сортировку и агрегацию. На большой базе становится заметна стоимость этих операций.
14. **Когда кеш не окупается?** При низкой повторяемости, дешёвом SQL, больших ответах или частых инвалидациях накладные расходы могут превысить выигрыш.
15. **Что делать при ежесекундных изменениях?** Измерить долю HIT, сузить область инвалидации, пересмотреть TTL. Для отчёта можно использовать периодически обновляемую агрегированную таблицу, если допустима задержка обновления.
