# Кеширование в EventManager

Клиент, REST API, схема предметной области и роли взяты из лабораторной № 9. Кеш подключён к маршрутам чтения после проверки токена. Данные общие для авторизованных ролей, поэтому токен в ключ не входит. Вход, выход и проверка прав выполняются через PostgreSQL.

## Алгоритм cache-aside

1. Проверить настройки и соединение с Redis через phpredis. Для подключения и чтения действуют тайм-ауты по 250 мс.
2. Прочитать актуальную версию набора из PostgreSQL, собрать ключ и выполнить Redis `GET`.
3. При попадании декодировать JSON и вернуть `X-Cache: HIT`.
4. При промахе выполнить запрос к PostgreSQL, сохранить JSON через `SETEX` и вернуть `X-Cache: MISS`.
5. При недоступности Redis или отключённом кеше выполнить исходный запрос к PostgreSQL и вернуть `X-Cache: BYPASS`.

Префикс по умолчанию — `eventapp:`. Для тестовой и рабочей баз задаются разные префиксы через `REDIS_PREFIX`. Команда очистки использует `SCAN` только по префиксу приложения.

| Данные | Ключ после префикса | Базовый TTL | Обоснование |
|---|---|---:|---|
| Площадки | `venues:list:v<версия>:<md5>` | 300 с | Часто нужны клиенту при входе. Справочник мал, меняется редко. |
| Категории | `categories:list:v<версия>:<md5>` | 300 с | Часто используются в форме. Изменения редкие, запрос простой. |
| Карточка | `events:item:<id>:v<версия>` | 60 с | Повторные просмотры возможны, но чтение по первичному ключу уже быстрое. |
| Списки мероприятий | `events:list:v<версия>:<md5>` | 60 с | Меняются чаще справочников. Поиск, сортировка и глубокая пагинация могут быть дорогими. |
| Сводка по площадкам | `report:summary:v<версия>` | 120 с | Агрегирует мероприятия через `JOIN` и `GROUP BY`. Повторное чтение экономит вычисления. |

Карточки справочников получают ключ `<ресурс>:item:<id>:v<версия>` с базовым TTL 60 с. В хеш списков входят условия и значения фильтров, сортировка, номер страницы и лимит. SQL использует идентификатор как дополнительный критерий сортировки при одинаковых датах или названиях.

Дополнительная возможность — случайная прибавка 0–15 % к TTL. Для 60, 120 и 300 секунд верхние границы составляют 69, 138 и 345 секунд. Разброс уменьшает вероятность одновременного истечения ключей, заполненных в одном интервале.

## Инвалидация

| Что изменилось | Что исключается из чтения |
|---|---|
| Мероприятие, POST / PUT / PATCH / DELETE | Прежние карточки и списки мероприятий, прежняя сводка. |
| Площадка, POST / PUT / PATCH / DELETE | Прежние карточки и списки площадок, прежняя сводка. |
| Категория, POST / PUT / PATCH / DELETE | Прежние карточки и списки категорий. |

Триггеры меняют UUID версии в той же транзакции PostgreSQL, что и запись данных. После успешного изменения ключ строится с новой версией. Старые ключи удаляет Redis по TTL. Незавершённый параллельный запрос может заполнить ключ старой версии, но последующие запросы его не используют. Изменения, выполненные при остановленном Redis, тоже обновляют версии. После восстановления Redis приложение заполняет кеш свежими данными. При изменении одной карточки сбрасывается целый набор карточек ресурса. Это упрощает схему версий ценой дополнительных промахов при активной записи.

## Для эксплуатации

Нужны мониторинг задержек и ошибок Redis, метрики попаданий, лимит памяти с подходящей политикой вытеснения, ограничения частоты попыток входа, HTTPS и отдельные учётные данные. Учебный режим `APP_DEBUG` и демонстрационные пароли следует отключить.
