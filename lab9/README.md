# Лабораторная работа №9. Интеграция компонентов веб-приложения

**Модуль:** Разработка web приложений  
**Предметная область:** EventManager — система управления мероприятиями.

## Цель

Интеграция браузерного клиента с REST API и PostgreSQL, реализация аутентификации, ролевой авторизации и комплексного тестирования.

## Архитектура

`Браузер (HTML/CSS/JavaScript) → fetch /api → PHP 8.2 (валидация, токены, роли) → PDO → PostgreSQL 16`.

Клиент доступен по `/client/`, серверное API — по `/api/`. Встроенный PHP-сервер обслуживает оба компонента с одного origin. JSON-файлы и `mock-api.js` не используются. Схема интеграции: `diagrams/src/integration.puml`. Реляционная схема: `diagrams/src/database.puml` (на основе лабораторной работы №8).

## Запуск

Требования: Docker Compose, PHP 8.2+, расширения `pdo_pgsql`, `curl`, `mbstring`.

```bash
cd lab9/src
docker compose up -d
php bin/reset-db.php
php -S localhost:8000 -t public public/router.php
```

Клиент: `http://localhost:8000/client/`. API: `http://localhost:8000/api/events` (требуется токен). В отдельном терминале:

```bash
cd lab9/src
php tests/api-tests.php
```

Сброс базы (`php bin/reset-db.php`) **удаляет данные в базе eventapp** и восстанавливает демонстрационный набор. Не запускать на рабочей базе. При занятом порте PostgreSQL: `DB_PORT=5433 docker compose up -d`, затем передать такой же `DB_PORT` командам PHP. Для PowerShell: `$env:DB_PORT=5433` перед запуском каждой команды. Для Windows запуск PHP: `php -S localhost:8000 -t public public/router.php`.

Если база недоступна, сервер возвращает 503. Настройки БД читаются из `DB_HOST`, `DB_PORT`, `DB_NAME`, `DB_USER`, `DB_PASSWORD`. Тестовые значения по умолчанию: localhost:5432, eventapp, postgres/secret.

## Ресурсы API

| Ресурс | URL | Операции |
|---|---|---|
| Мероприятия | `/api/events`, `/api/events/{id}` | GET, POST, PUT/PATCH, DELETE |
| Площадки | `/api/venues`, `/api/venues/{id}` | GET, POST, PUT/PATCH, DELETE |
| Категории | `/api/categories`, `/api/categories/{id}` | GET, POST, PUT/PATCH, DELETE |
| Аутентификация | `/api/auth/login`, `/api/auth/me`, `/api/auth/logout` | POST, GET, POST |

Пример получения списка: `GET /api/events?status=planned&sort=-id` с `Authorization: Bearer <token>` → `200 OK`, массив объектов.

Пример создания: `POST /api/events` с `{"title":"Семинар","venue_id":1,"category_id":2,"starts_at":"2027-07-01T10:00:00+03:00","ends_at":"2027-07-01T12:00:00+03:00"}` → `201 Created`, заголовок Location.

Пример изменения: `PATCH /api/events/1` с `{"status":"completed"}` → `200 OK`.

Пример удаления: `DELETE /api/events/1` с токеном manager → `204 No Content`.

Полная спецификация: `docs/api.md`.

## Согласование контракта клиента и сервера

| Аспект | Согласованное решение |
|---|---|
| Адреса | `/api/events`, `/api/venues`, `/api/categories` |
| Поля дат | `starts_at` и `ends_at`, ISO 8601 |
| Ссылки | `venue_id`, `category_id` передаются числами |
| Сортировка | `sort=-id`, а не `_sort=id&_order=desc` |
| Ошибки | `error` и `errors` (объект ошибок полей) |
| Авторизация | `Authorization: Bearer <token>` |
| Пустое описание | `null`, а не пустая строка |
| Нет связи | Ошибка fetch отдельно от HTTP 4xx/5xx |

Вводимые значения отображаются через `textContent` без вставки HTML. Поиск имеет задержку 300 мс и игнорирует устаревшие ответы. Кнопка отправки блокируется до завершения запроса.

## Пользовательский сценарий

Вход manager → просмотр мероприятий → поиск → фильтр → создание → завершение → удаление → выход → вход editor → проверка отсутствия кнопки удаления → прямой запрос DELETE с результатом 403 → проверка недоступности сервера и базы.

## Тестирование

Автотесты находятся в `src/tests/api-tests.php`: вход, 401/403, защита токена, CRUD трёх ресурсов, валидация, конфликт связей, фильтры и выход. Сценарии браузерного тестирования и безопасности: `docs/testing.md`.

**Статус проверки:** PHP-файлы проверяются синтаксически. Полный прогон PostgreSQL, HTTP-автотестов и браузерных сценариев необходимо выполнить в установленном окружении. Фактические результаты и скриншоты не подменяются предположениями.

## Ограничения учебной реализации

Приложение работает по HTTP на localhost, использует демонстрационные учётные записи и пароль базы, хранит токен в localStorage; для промышленного применения нужны HTTPS, защищённые cookie, миграции схемы, rate limiting, аудит и секреты из безопасного хранилища.

## Вывод

Подготовлена интегрированная архитектура клиентского приложения, PHP REST API и PostgreSQL с проверкой полномочий, обработкой ошибок и автоматизированными HTTP-тестами. Окончательная оценка работоспособности выполняется после развёртывания и прохождения всех сценариев.
